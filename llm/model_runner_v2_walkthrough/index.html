Model Runner V2: Code Walkthrough

This document explains the execution path of Model Runner V2 (MRV2), centered on vllm/v1/worker/gpu/model_runner.py. It is intended as a code-reading guide. The higher-level design rationale is in model_runner_v2.md.

MRV2 is a per-worker orchestration layer. It does not implement transformer layers. Instead, it connects scheduler state, GPU-resident request state, attention/KV-cache metadata, CUDA graphs, the model, sampling, and output processing.

1. Code structure

flowchart TD
    S["SchedulerOutput"] --> R["GPUModelRunner.execute_model"]
    R --> U["Update request and KV state"]
    U --> I["prepare_inputs"]
    I --> A["prepare_attn"]
    A --> D["dispatch_cg_and_sync_dp"]
    D --> M["ModelState.prepare_inputs / prepare_attn"]
    M --> F["Model forward: eager, PIECEWISE, or FULL CUDA graph"]
    F --> X["ExecuteModelState"]
    X --> T["sample_tokens"]
    T --> L["Compute logits and sample"]
    L --> P["postprocess_sampled"]
    P --> G["Speculator proposal and KV connector"]
    G --> O["AsyncOutput / ModelRunnerOutput"]

    R -. "last PP rank" .-> T
    R -. "non-last PP rank" .-> PP["IntermediateTensors"]

    RS["RequestState"] --> I
    IB["InputBuffers / InputBatch"] --> I
    BT["BlockTables / KV cache"] --> A
    CG["ModelCudaGraphManager"] --> D
    MS["DefaultModelState or model-specific state"] --> M
    K["Triton input/update kernels"] --> I
    K --> P

The main state objects have deliberately different lifetimes:

Object Lifetime Responsibility
RequestState Persistent across steps Fixed slots for request IDs, token history, computed-token counters, draft tokens, and sequence limits.
InputBuffers Persistent buffers reused by steps GPU buffers for token IDs, positions, query offsets, and sequence lengths.
InputBatch One forward step The current request ordering, mappings, lengths, logits positions, and views into InputBuffers.
ModelState Persistent model-specific state RoPE, multimodal inputs, encoder-decoder state, Mamba state, and model-specific attention metadata.
ExecuteModelState Between forward and output processing Hidden states and metadata retained for sample_tokens() or pool().
BlockTables Persistent Maps logical request positions to paged KV-cache blocks and computes slot mappings.
ModelCudaGraphManager Persistent after KV initialization Captures and dispatches compatible CUDA graphs.

The runner is created by the worker when use_v2_model_runner is enabled; see gpu_worker.py around the MRV2 construction branch.

2. Lifecycle of one step

The public step is split into a forward phase and a result phase:

SchedulerOutput
      |
      v
execute_model()
      |-- request/KV state updates
      |-- input and attention metadata preparation
      |-- model forward
      `-- save ExecuteModelState
                |
                v
sample_tokens() or pool()
      |-- logits/sampling or pooling
      |-- update GPU request state
      |-- speculative draft proposal
      `-- asynchronous output copy

This split is important for asynchronous scheduling. The engine can enqueue a forward and then enqueue sampling without synchronously materializing the result on the host. See EngineCore.step_with_batch_queue() and AsyncOutput.

3. execute_model

GPUModelRunner.execute_model() coordinates everything needed to launch one model forward.

3.1 Update persistent request state

For a real batch, the runner first processes lifecycle changes:

self.update_pp_decode_requests()
self.finish_requests(scheduler_output)
self.free_states(scheduler_output)
self.add_requests(scheduler_output)
self.update_requests(scheduler_output)
self.block_tables.apply_staged_writes()

This is at model_runner.py:1217.

The operations include:

  • Removing finished and preempted requests.
  • Adding new or resumed requests into fixed RequestState slots.
  • Updating the CPU mirror of num_computed_tokens for cached requests.
  • Appending newly allocated KV-cache blocks.
  • Zeroing fresh cache blocks when required.
  • Applying copy-on-write KV-cache block copies.

New request data is staged before the forward. RequestState.apply_staged_writes() then commits token history, lengths, and the initial computed-token count to the GPU/UVA-visible state.

If there are no scheduled tokens, the runner skips the model and asks the KV connector for a no-forward result.

3.2 Select the execution shape

The runner derives:

num_reqs = len(scheduler_output.num_scheduled_tokens)
num_toks = scheduler_output.total_num_scheduled_tokens
max_query_len = max(scheduler_output.num_scheduled_tokens.values())
uniform_tok_count = get_uniform_token_count(
    num_reqs, num_toks, max_query_len
)

It also accounts for active LoRA adapters and forces eager execution for some dynamic encoder-decoder updates. Then it calls dispatch_cg_and_sync_dp().

The returned BatchExecutionDescriptor contains the selected:

  • CUDA graph mode: NONE, PIECEWISE, or FULL.
  • Padded token count.
  • Padded request count, when needed.
  • Uniform token count, when applicable.
  • Effective active-LoRA capture case.

3.3 Prepare the InputBatch

For real work, execute_model() calls:

input_batch = self.prepare_inputs(scheduler_output, batch_desc)
block_tables, slot_mappings = self.prepare_attn(input_batch)

These are described in the next sections. The important distinction is that RequestState stores persistent state in stable request slots, while InputBatch gathers those slots into the order required by this step.

3.4 Prepare model-specific and multimodal inputs

The first pipeline rank may run a multimodal encoder and produce inputs_embeds. Then the model-specific state contributes additional inputs:

model_inputs = {
    "input_ids": input_ids,
    "positions": input_batch.positions,
    "inputs_embeds": inputs_embeds,
    "intermediate_tensors": None,
    **self.model_state.prepare_inputs(input_batch, self.req_states),
}

For non-first pipeline ranks, token IDs and embeddings are removed and the received IntermediateTensors are copied into persistent buffers. This is needed because CUDA graphs require stable addresses.

3.5 Run the model

There are three execution paths:

if batch_desc.cg_mode == CUDAGraphMode.FULL:
    model_output = self.cudagraph_manager.run_fullgraph(batch_desc)
elif batch_desc.cg_mode == CUDAGraphMode.PIECEWISE:
    model_output = self.cudagraph_manager.run_pw_graph(
        self.model, model_inputs
    )
else:
    model_output = self.model(**model_inputs)

The actual code wraps the eager and piecewise paths in set_forward_context(), which publishes attention metadata, slot mappings, padding, DP token counts, and the runtime CUDA-graph mode to the model and attention layers. See model_runner.py:1385.

3.6 Save the forward result

The last pipeline rank receives hidden states. Earlier ranks receive IntermediateTensors. MRV2 saves the result in:

self.execute_model_state = ExecuteModelState(
    input_batch=input_batch,
    attn_metadata=attn_metadata,
    slot_mappings_by_layer=slot_mappings_by_layer,
    hidden_states=hidden_states,
    aux_hidden_states=aux_hidden_states,
    finished_req_ids=finished_req_ids,
)

See model_runner.py:1440.

  • Non-last pipeline ranks return IntermediateTensors immediately.
  • The last rank returns None; the caller then invokes sample_tokens().

4. prepare_inputs

prepare_inputs() converts the scheduler’s ragged per-request token counts into a contiguous GPU input layout.

4.1 Request ordering and slot mapping

MRV2 orders requests as decode, short extension, then prefill. It builds:

  • req_ids: request order for this step.
  • idx_mapping: batch row → persistent RequestState slot.
  • idx_mapping_np: host version used for bookkeeping.
  • expanded_idx_mapping: per-logit mapping used by speculative decoding.

The batch row does not have to equal the persistent request slot. This indirection is what allows requests to retain stable state while each step uses an execution-friendly order.

4.2 Query offsets and padding

query_start_loc is the cumulative sum of scheduled tokens:

query_start_loc = [0,
                   q0,
                   q0 + q1,
                   ...]

The host constructs a NumPy copy and asynchronously copies it into the persistent GPU input buffer. CUDA-graph padding extends the buffer without changing the unpadded request semantics.

4.3 Prefill tokens

When a request is still prefilling, prepare_prefill_inputs() gathers the next query tokens from persistent all_token_ids. This gather happens in a Triton kernel so the GPU can read the request state directly, including UVA-backed storage.

4.4 Positions and sequence lengths

prepare_pos_seq_lens() reads the GPU req_states.num_computed_tokens.gpu and writes:

position[b, j] = num_computed_tokens[state_slot] + j
seq_lens[b]    = num_computed_tokens[state_slot] + query_len[b]

The host also builds seq_lens_cpu_upper_bound from the scheduler-side mirror:

num_computed_tokens_np = (
    self.req_states.num_computed_tokens_np[idx_mapping_np]
)
seq_lens_cpu_upper_bound_np = np.zeros(num_reqs_padded, dtype=np.int32)
np.add(
    num_computed_tokens_np,
    num_scheduled_tokens,
    out=seq_lens_cpu_upper_bound_np[:num_reqs],
)

See model_runner.py:1059.

This CPU value is a planning upper bound. It avoids a GPU-to-CPU readback on the common path. It can be optimistic for asynchronous speculative decoding, where the host does not yet know which draft tokens will be rejected.

4.5 Sampled and draft tokens

For autoregressive decode, the input can contain:

  1. The previous sampled token.
  2. Scheduled draft tokens.
  3. A target-model bonus position.

combine_sampled_and_draft_tokens() writes those token IDs into the right input positions and returns logits_indices, which identifies the hidden-state rows that should produce logits.

4.6 Result

The method packages all of these views and mappings in InputBatch, including:

  • input_ids, positions, and is_padding.
  • query_start_loc and seq_lens.
  • seq_lens_cpu_upper_bound.
  • logits_indices and cumulative logit ranges.
  • Prefill flags and prompt lengths.

The optional PCP manager may then partition the batch before returning it.

5. prepare_attn

prepare_attn() turns request indices and positions into paged-attention metadata.

For the normal path it:

  1. Gathers each request’s persistent block-table row into the current batch order.
  2. Computes a slot mapping for each scheduled token.
  3. Returns block tables and slot mappings for all KV-cache groups.
block_tables = self.block_tables.gather_block_tables(
    input_batch.idx_mapping,
    num_reqs_padded=input_batch.num_reqs_after_padding,
)
slot_mappings = self.block_tables.compute_slot_mappings(
    input_batch.idx_mapping,
    input_batch.query_start_loc,
    input_batch.positions,
    num_tokens_padded=input_batch.num_tokens_after_padding,
)

See model_runner.py:1113.

block_tables answer “which physical KV blocks belong to each request?”; slot_mappings answer “which physical KV slot corresponds to each query token?” The attention backend consumes both.

PCP has a specialized preparation path because the logical batch is partitioned before attention metadata is built. Dummy attention metadata is used for profiling and CUDA-graph capture.

6. dispatch_cg_and_sync_dp

dispatch_cg_and_sync_dp() combines two decisions:

  1. Select a compatible CUDA-graph descriptor locally.
  2. Make the execution shape consistent across data-parallel ranks.

For a single DP rank, it simply returns the local descriptor. With multiple DP ranks, sync_cudagraph_and_dp_padding() performs an all-reduce over a small CPU tensor containing:

per-rank token count
per-rank requested CUDA-graph mode
per-rank uniform token count

The synchronization rules are:

  • If all ranks have zero tokens, all ranks skip the forward.
  • If any rank requires eager mode, all ranks use eager mode.
  • Otherwise, the maximum token count is used for a common padded descriptor.
  • Uniform decode is retained only if all ranks agree on the uniform count.

The core logic is in dp_utils.py:16. The resulting num_tokens_across_dp is passed to set_forward_context() so DP-aware kernels know the common execution size.

7. sample_tokens

sample_tokens() consumes the ExecuteModelState produced by the preceding forward.

7.1 Non-last pipeline ranks

Earlier pipeline ranks do not have final hidden states. They receive sampled tokens from the last rank through PPHandler:

all_decode_next = self.pp_handler.receive(input_batch)
self.postprocess_num_computed_tokens(input_batch)

The initial update is optimistic. A later deferred postprocess_sampled() call applies the exact rejection correction when the broadcasted result is consumed. See model_runner.py:1472.

7.2 Last pipeline rank

The last rank:

  1. Restores the original PCP batch if PCP was used.
  2. Selects hidden states at input_batch.logits_indices.
  3. Computes logits.
  4. Applies structured-output grammar masks.
  5. Runs normal sampling or speculative rejection sampling.
  6. Broadcasts sampled tokens and acceptance counts to earlier PP ranks.
  7. Computes prompt logprobs.
  8. Creates AsyncOutput for an overlapping output copy.
  9. Calls postprocess_sampled().
  10. Runs the speculative drafter, if configured.
  11. Performs KV-connector post-forward work.

The sampling decision is implemented by sample():

sample_hidden_states = hidden_states[input_batch.logits_indices]
logits = self.model.compute_logits(sample_hidden_states)

if grammar_output is not None:
    self.structured_outputs_worker.apply_grammar_bitmask(...)

if input_batch.num_draft_tokens == 0:
    sampler_output = self.sampler(logits, input_batch)
else:
    sampler_output = self.rejection_sampler(...)

See model_runner.py:1143.

The output copy is launched before request-state postprocessing so that the device-to-host copy can overlap with state updates and speculative drafting:

async_output = AsyncOutput(...)
self.postprocess_sampled(...)

See model_runner.py:1527.

8. postprocess_sampled

postprocess_sampled() updates GPU-side request state after sampling. It calls post_update(), which updates:

  • last_sampled_tokens.
  • all_token_ids.
  • total_len.
  • Sampling penalty counters.
  • num_computed_tokens.gpu.

The computed-token delta is:

scheduled query length - rejected speculative tokens

Then it calls model_state.postprocess_state(), allowing Mamba/hybrid or other model-specific state to advance.

The scheduler’s host-side Request.num_computed_tokens is not read from this GPU tensor. The scheduler already advanced its own counter at schedule time and later reconciles rejected tokens when it processes the returned output.

9. DefaultModelState

GPUModelRunner delegates model-specific behavior to a ModelState object. The selection logic is in model_states/__init__.py:

  1. A model-provided custom state, if available.
  2. EncoderDecoderModelState for cross-attention models.
  3. EncoderOnlyModelState for encoder-only models.
  4. MambaHybridModelState for hybrid models.
  5. DefaultModelState otherwise.

DefaultModelState handles the common decoder-only path. It owns or coordinates:

  • RoPE position state.
  • Optional multimodal embedding pruning.
  • Multimodal encoder execution and embedding assembly.
  • Model-specific position overrides.
  • Common attention metadata construction.

DefaultModelState.prepare_attn

The method first chooses padded or unpadded dimensions:

if cudagraph_mode == CUDAGraphMode.FULL:
    num_reqs = input_batch.num_reqs_after_padding
    num_tokens = input_batch.num_tokens_after_padding
else:
    num_reqs = input_batch.num_reqs
    num_tokens = input_batch.num_tokens

It then prepares both host and device query offsets:

query_start_loc_cpu = torch.from_numpy(
    input_batch.query_start_loc_np[: num_reqs + 1]
)
query_start_loc_gpu = input_batch.query_start_loc[: num_reqs + 1]

For normal execution, max_seq_len is derived from the CPU upper bound. During capture, it uses max_model_len so the graph remains valid for later replays.

Finally, it calls build_attn_metadata() with both forms of sequence metadata:

attn_metadata = build_attn_metadata(
    ...,
    query_start_loc_gpu=query_start_loc_gpu,
    query_start_loc_cpu=query_start_loc_cpu,
    seq_lens=input_batch.seq_lens,
    max_seq_len=max_seq_len,
    seq_lens_cpu_upper_bound=seq_lens_cpu_upper_bound,
    dcp_local_seq_lens=input_batch.dcp_local_seq_lens,
    positions=input_batch.positions,
    is_prefilling=torch.from_numpy(input_batch.is_prefilling_np),
    ...,
)

See default.py:135 and attn_utils.py:500.

build_attn_metadata() creates a CommonAttentionMetadata object for each KV cache group and invokes that group’s backend metadata builder. The GPU seq_lens is available for device-side execution; the CPU upper bound supports host-side planning such as maximum context lengths and DCP decisions.

10. Triton kernels in input_batch.py

The kernels in input_batch.py move per-step input preparation and state updates onto the GPU. They are not separate model stages; they prepare the buffers consumed by the model and sampler.

10.1 prepare_prefill_inputs

For each batch request, the kernel:

  1. Maps the batch row to a persistent request slot.
  2. Reads num_computed_tokens and prefill_len.
  3. Copies the next query range from all_token_ids into input_ids.
  4. Stores a small lookahead window in next_prefill_tokens for MTP/speculative modules.

This is a straightforward indexed gather; the Triton version avoids a Python loop and can read UVA-backed token history.

10.2 prepare_pos_seq_lens

For each request row it computes positions and the total sequence length after the current query. It also zeros unused rows for FULL CUDA graphs.

A readable, unoptimized reference implementation is:

def prepare_pos_seq_lens_ref(
    idx_mapping: torch.Tensor,          # [num_reqs], device
    query_start_loc: torch.Tensor,      # [num_reqs + 1], device
    num_computed_tokens: torch.Tensor,  # [max_num_reqs], device
    positions: torch.Tensor,            # [max_num_tokens], device
    seq_lens: torch.Tensor,             # [max_num_reqs], device
) -> None:
    num_reqs = idx_mapping.shape[0]

    for batch_idx in range(num_reqs):
        state_idx = int(idx_mapping[batch_idx])
        start = int(query_start_loc[batch_idx])
        end = int(query_start_loc[batch_idx + 1])
        query_len = end - start
        computed = int(num_computed_tokens[state_idx])

        positions[start:end] = torch.arange(
            computed,
            computed + query_len,
            device=positions.device,
            dtype=positions.dtype,
        )
        seq_lens[batch_idx] = computed + query_len

    # Required by FULL CUDA-graph replay.
    seq_lens[num_reqs:] = 0

The production kernel is _prepare_pos_seq_lens_kernel() at input_batch.py:267.

10.3 combine_sampled_and_draft_tokens

This kernel handles the non-contiguous relationship between model input tokens and logits during speculative decoding. It:

  • Computes the positions of the final target/draft logits.
  • Writes the previous sampled token into the first generated-token position.
  • Writes draft tokens into the subsequent positions.
  • Returns the hidden-state indices that should be passed to compute_logits().

For a single request, the conceptual operation is:

def combine_sampled_and_draft_tokens_ref(
    input_ids: torch.Tensor,
    last_sampled_token: int,
    draft_tokens: torch.Tensor,
    query_start: int,
    query_end: int,
    seq_len: int,
    prefill_len: int,
    num_new_sampled_tokens: int = 1,
) -> torch.Tensor:
    num_draft = draft_tokens.numel()
    num_logits = num_new_sampled_tokens + num_draft
    logits_start = query_end - num_logits
    logits_indices = torch.arange(
        logits_start, query_end, device=input_ids.device
    )

    # During decode, the first generated-token input is the previous sample.
    first_logit_seq_pos = seq_len - num_logits
    if (
        num_new_sampled_tokens > 0
        and first_logit_seq_pos >= prefill_len
    ):
        input_ids[logits_start] = last_sampled_token

    if num_draft > 0:
        input_ids[query_end - num_draft:query_end] = draft_tokens

    return logits_indices

The actual implementation supports ragged batches and writes all per-request logit indices into one contiguous tensor. See input_batch.py:325.

10.4 post_update

post_update() applies the result of sampling back to persistent GPU state. For each request it:

  1. Stores the final sampled token as last_sampled_tokens.
  2. Appends sampled tokens to all_token_ids.
  3. Increments total_len by the number of sampled tokens.
  4. Updates penalty counters.
  5. Advances num_computed_tokens by query length minus rejected draft tokens.

The following reference implementation omits Triton parallelism and CUDA-stream details but mirrors the state transitions:

def post_update_ref(
    idx_mapping: torch.Tensor,          # [num_reqs]
    num_computed_tokens: torch.Tensor,  # [max_num_reqs]
    last_sampled_tokens: torch.Tensor,  # [max_num_reqs, 1]
    sampled_tokens: torch.Tensor,       # [num_reqs, max_sample_len]
    num_sampled: torch.Tensor,          # [num_reqs]
    num_rejected: torch.Tensor,         # [num_reqs]
    query_start_loc: torch.Tensor,      # [num_reqs + 1]
    all_token_ids: torch.Tensor,        # [max_num_reqs, max_model_len]
    total_len: torch.Tensor,            # [max_num_reqs]
) -> None:
    for batch_idx in range(idx_mapping.shape[0]):
        state_idx = int(idx_mapping[batch_idx])
        if state_idx < 0:
            continue

        n_sampled = int(num_sampled[batch_idx])
        n_rejected = int(num_rejected[batch_idx])
        old_total_len = int(total_len[state_idx])

        if n_sampled > 0:
            tokens = sampled_tokens[batch_idx, :n_sampled]
            all_token_ids[
                state_idx, old_total_len:old_total_len + n_sampled
            ] = tokens
            last_sampled_tokens[state_idx, 0] = tokens[-1]
            total_len[state_idx] = old_total_len + n_sampled

        query_len = int(
            query_start_loc[batch_idx + 1] - query_start_loc[batch_idx]
        )
        num_computed_tokens[state_idx] += query_len - n_rejected

The production kernel is _post_update_kernel() at input_batch.py:480.

10.5 post_update_num_computed_tokens

This simpler kernel only adds each row’s query length to the GPU computed-token counter. It is used for pooling and for the optimistic non-last-PP path, where the exact sampled/rejected result is applied later:

num_computed_tokens[state_idx] += query_start_loc[i + 1] - query_start_loc[i]

See input_batch.py:582 and model_runner.py:1646.

11. Asynchronous computed-token synchronization

The scheduler and worker do not synchronize by reading the GPU counter back to the CPU. Instead:

Scheduler schedules batch i
  -> host num_computed_tokens advances optimistically
  -> SchedulerOutput carries the old starting count to the worker
  -> GPU prepares positions/seq_lens from its GPU counter
  -> GPU postprocess advances its GPU counter
  -> sampled output returns to the scheduler
  -> scheduler rolls back rejected/stale speculative tokens

The scheduler therefore has a reconciled prefix followed by an optimistic in-flight suffix. With a queue size of two, when scheduling batch i+2, batch i is normally already reconciled while batch i+1 may still be optimistic. With a larger queue, multiple later batches may remain optimistic.

This design preserves overlap while keeping the GPU’s execution state exact. The host-side num_computed_tokens is authoritative for scheduling decisions; the runner-side GPU tensor is authoritative for the currently executing GPU metadata and model state.

12. Suggested reading order

For a new code reader, the following order is effective:

  1. GPUModelRunner.__init__() to see persistent components.
  2. execute_model() for the complete forward lifecycle.
  3. prepare_inputs() and InputBatch for batch layout.
  4. prepare_attn() and DefaultModelState.prepare_attn() for attention metadata.
  5. dispatch_cg_and_sync_dp() for execution-shape coordination.
  6. sample_tokens() and postprocess_sampled() for sampling and state advancement.
  7. input_batch.py for the GPU kernels that connect request state to model inputs and outputs.
