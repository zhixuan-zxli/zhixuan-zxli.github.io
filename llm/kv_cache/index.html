1. Initialization of KV Caches

EngineCore._initialize_kv_caches

  1. Retrieve the kv_cache_specs.
  2. Generate the configuration via get_kv_cache_configs.
  3. Call initialize_from_config, which calls GPUModelRunner.initialize_kv_cache.

GPUModelRunner.get_kv_cache_spec

  • Enumerates all attention layers.
  • For each layer, calls Attention.get_kv_cache_spec.
  • Returns a Dict[layer_name: str, AttentionSpec].

get_kv_cache_configs (from kv_cache_utils.py) groups specs and produces a unified configuration.

  1. get_kv_cache_groups → _get_kv_cache_groups_uniform_spec / uniform_page_size
    Returns list[KVCacheGroupSpec(layer_names, KVCacheSpec)].
  2. get_kv_cache_config_from_groups
    Returns a KVCacheConfig containing:
    • num_blocks
    • kv_cache_tensors: list[KVCacheTensor(size, shared_by: list[str])] – length equals max group size.
    • kv_cache_groups: list[KVCacheGroupSpec]

Notes:

  • MambaSpec cannot merge with FullAttentionSpec.
  • unify_kv_cache_spec_page_size adjusts block sizes for some specs; for already‑padded Qwen3‑Next Mamba, no operation is performed.

GPUModelRunner.initialize_kv_cache

  • initialize_attn_backend
  • initialize_metadata_builders
  • initialize_kv_cache_tensors:
    • _allocate_kv_cache_tensors(kv_cache_config) - Returns raw tensors per group: dict[layer_name: str, torch.Tensor].
    • _reshape_kv_cache_tensors(kv_cache_config, kv_cache_raw_tensors, kernel_block_size),
      where kernel_block_size is the block size per group. Returns a sliced dictionary dict[layer_name: str, tuple[torch.Tensor]].
    • bind_kv_cache
      1. Sets self.kv_caches to a list of tuples (sorted by layer index).
      2. Configures the KV caches of forward_context[layer_name] (e.g., for Qwen3NextGatedDeltaNet).

3. Zero-bubble async scheduling

Here’s a walkthrough of PR #32951 based on the diff, description, and the predecessor PR #29957.

What the PR does

Before this PR, async scheduling + speculative decoding still had a synchronization bubble. Concretely, at the top of each step’s _update_states, the CPU had to wait for the GPU to hand back valid_sampled_token_count from the previous step’s rejection sampler in order to know how many of the drafted tokens the target model actually accepted. Only then could it compute correct num_computed_tokens, seq_lens, positions, and slot mapping for the next step. The CPU-side prep therefore only overlapped with the draft forward, not with the target forward — leaving a bubble on the GPU.

This PR refactors things so the CPU side optimistically assumes every draft token was accepted and lays out the next batch immediately, without waiting on any GPU→CPU copy. The mistake, if any, is later corrected — on the GPU inside _prepare_inputs, and on the CPU only after the target forward has already been launched.

It is a refactor of #29957 by @izhuhaoran, adopting the model-runner-V2 compute_slot_mappings_kernel (plus @yewentao256’s changes from #34179) into V1.

How it achieves zero bubble

Three main mechanisms:

  1. Optimistic CPU prep (removes the wait). In vllm/v1/worker/gpu_model_runner.py, _update_states no longer calls self._get_valid_sampled_token_count() inline. Instead, for each request that had drafts, it assumes num_accepted = req_state.prev_num_draft_len (all accepted), extends output_token_ids with -1 placeholders accordingly, and stashes the request in a deferred_spec_decode_corrections list. It returns a correct_spec_decode_token_counts() closure to be called later.

_prepare_inputs then builds an optimistic_seq_lens_cpu = num_computed_tokens_cpu + num_scheduled_tokens under that optimistic assumption, and uses it for everything CPU-visible (max_seq_len, discard_request_mask, MRoPE, DCP local seq lens, pooling cursor).

  1. GPU-side correction (fixes the optimism before the kernel sees it). The new update_num_computed_tokens_for_batch_change triton/torch.compiled op in vllm/v1/spec_decode/utils.py runs in _prepare_inputs. It takes the previous step’s valid_sampled_token_count_gpu (which is still valid on the GPU without ever being copied to the CPU), the prev_positions map (current-batch idx → previous-batch idx), and the CPU’s (optimistic) num_computed_tokens, and writes a corrected num_computed_tokens GPU tensor:
  • Requests that had drafts last step: corrected = prev_num_computed_tokens_gpu + valid_count_gpu
  • New requests / non-draft rows: use the CPU value directly

The GPU is now the source of truth for num_computed_tokens, seq_lens, and positions. That’s why seq_lens, positions, and num_computed_tokens become plain GPU tensors (not CpuGpuBuffers), and the CommonAttentionMetadata is passed _seq_lens_cpu=None, _num_computed_tokens_cpu=None when use_async_spec_decode is on.

  1. Deferred CPU correction (fixes the CPU bookkeeping after launch). After execute_model has finished issuing all the target-model kernels, it finally calls deferred_state_corrections_fn(). That closure syncs on _get_valid_sampled_token_count() and rolls back req_state.num_computed_tokens, input_batch.num_computed_tokens_cpu, and num_tokens_no_spec by (optimistic - actual). Because the kernels are already queued, the CPU stall no longer blocks the GPU — the next step can be fully prepared before it fires.

Two supporting changes keep everything consistent:

  • Slot mapping moved to the GPU. block_table.compute_slot_mapping was a numpy computation from req_indices/positions on the CPU. Now it’s the _compute_slot_mapping_kernel triton kernel driven by query_start_loc and the (corrected) GPU positions. commit_slot_mapping (the H2D copy of the slot mapping) is deleted — the slot mapping is written directly on device. This is required because positions are only correct on the GPU now.
  • update_async_output_token_ids is patched to allow the placeholder list to shrink, since optimistic placeholders may exceed the eventual acceptance count.
  • Cascade attention is force-disabled when async + spec are both on (compatibility hole).

What changes vs your v0.14 mental model

The pre-PR flow on main (which is close to what you know from v0.14, in structure) was:

  1. _update_states calls _get_valid_sampled_token_count() → CPU waits on GPU copy of the previous step’s acceptance mask.
  2. Using the true acceptance counts, it decrements num_computed_tokens and appends the right number of -1 placeholders.
  3. _prepare_inputs computes positions and slot_mapping on the CPU with numpy (np.repeat, np.add, block_table.compute_slot_mapping iterating a numpy req_indices) using the correct num_computed_tokens_cpu, then H2D-copies them.
  4. seq_lens.np is built on CPU, then H2D-copied.
  5. num_accepted_tokens is populated in _build_attention_metadata under if use_spec_decode:, gated by num_accepted_tokens_event.

After this PR:

  1. _update_states never waits. It writes optimistic placeholders, records a deferred-correction closure, and populates prev_num_draft_tokens for later GPU use.
  2. _prepare_inputs builds optimistic_seq_lens_cpu (may be wrong by the reject count), then runs update_num_computed_tokens_for_batch_change on the GPU to make num_computed_tokens/num_accepted_tokens correct on the device without a sync. positions and seq_lens are computed on the GPU via num_computed_tokens[req_indices] + query_pos. slot_mapping is written by _compute_slot_mapping_kernel (triton) directly on the GPU.
  3. CommonAttentionMetadata passes _seq_lens_cpu=None, _num_computed_tokens_cpu=None for async spec — the attention backends must read GPU tensors. New request-added dtype changes: num_accepted_tokens is int32 (was int64).
  4. The old CPU seq_lens/positions/compute_slot_mapping paths are still used for the non-async-spec case (backward compat), toggled by self.use_async_spec_decode.
  5. After the target-model forward is dispatched at the end of execute_model, the deferred correction runs to reconcile CPU bookkeeping — a stall that now overlaps nothing critical because the GPU is already busy on the next batch.

One caveat worth noting: hybrid (mamba) models still take a .cpu() sync in update_states_after_model_execute (see the TODO in the diff), so full asynchrony there is not yet achieved. And with mamba_cache_mode == "align", the deferred CPU correction is forced to run before preprocess_mamba (which reads req_state.num_computed_tokens), then num_accepted_tokens is resynced to GPU.
