Mooncake KV Connectors in vLLM

vLLM ships two different KVConnectorBase_V1 implementations for Mooncake, with fundamentally different transfer architectures:

  • MooncakeConnector — direct P2P transfer via RDMA one-sided writes.
  • MooncakeStoreConnector — shared distributed KV pool keyed by content hash.

Source files:

  • vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py
  • vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/connector.py

1. MooncakeConnector — Direct P2P transfer

This is a P-push connector: the producer (prefiller) writes KV blocks directly into the consumer’s (decoder’s) memory via RDMA. It’s built on top of Mooncake’s TransferEngine, which does one-sided RDMA writes.

Architecture

  • Split into MooncakeConnectorScheduler (control-plane) and MooncakeConnectorWorker (data-plane), matching the standard vLLM connector role split.
  • Both P and D workers can coexist in one process (kv_both) — the code branches on is_kv_producer / is_kv_consumer.

Discovery: bootstrap server

  • Global-rank-0 P-worker launches an HTTP MooncakeBootstrapServer.
  • Every P-worker registers (engine_id, dp_rank, tp_rank, pp_rank, zmq_addr) with it.
  • D-workers hit the bootstrap /query endpoint on first contact with a new engine_id (_connect_to_prefiller_bootstrap), caching the topology in _remote_agents.

Metadata channel: ZMQ

  • P-worker binds a ZMQ ROUTER socket to a random port; that port is what gets registered with bootstrap.
  • D-worker uses a DEALER socket to send a MooncakeXferMetadata blob per pull request. That blob contains the D’s KV base addresses, block lengths, per-layer registrations, plus per-request (transfer_id, [[block_ids]]).
  • P responds with MooncakeXferResponse, streamed as CONTINUE messages while transfers finish incrementally and FINISH at the end.

KV registration

register_kv_caches iterates each layer’s KV tensor. Depending on the attention spec:

  • MLA / SlidingWindowMLA → treat whole layer as one region (page_size_bytes).
  • Mamba/GDN → register only the conv tensor.
  • Standard attention with virtually_split_kv_in_blocks layout → treat K and V halves as separate transfer regions (kv_block_len = block_len // 2). _expand_transfer_regions emits two TransferRegion entries per layer, one at base_addr and one at base_addr + kv_block_len.

All unique storage_addr regions are batch-registered with Mooncake’s RDMA layer via engine.batch_register_memory — this is what pins the memory for one-sided RDMA writes.

The actual transfer

_build_transfer_params is where block-level RDMA descriptors are computed:

  1. Group-aware block matching. Hybrid models can have multiple KV groups (e.g. full-attention pages + GDN inner-state slots). Block IDs from group i on P must only be paired with group i on D — the code carefully preserves per-group identity. For Mamba groups, NULL_BLOCK_ID placeholders are filtered out.
  2. Region alignment across PP shards. _align_transfer_regions matches registered regions by (layer_name, occurrence_order) rather than positionally, because P and D may have different PP layouts and thus own different layer subsets.
  3. Heterogeneous TP planning. _compute_sender_transfer_plan figures out, for a given (local_tp_rank, remote_tp_rank) pair:
    • Whether this rank sends at all (for replicated caches like MLA, only rank 0 within a TP group needs to send).
    • Source/dest byte offsets inside a KV block (when local TP > remote TP, one local rank writes into a slice of the remote block; when local TP < remote TP, one local rank gathers from multiple remote regions).
    • tp_ratio handles both directions with sign convention.
  4. Coalescing. group_concurrent_contiguous uses np.diff to find runs of contiguous block IDs on both sides. When a run is contiguous AND the per-block copy covers the full block (_can_coalesce_block_transfers), the whole run becomes one large descriptor instead of N small ones. Big win for RDMA throughput.
  5. Logical → kernel expansion (_logical_to_kernel_block_ids). When speculative decoding forces the effective kernel block size smaller than the logical one, each logical block ID expands to _physical_blocks_per_logical_kv_block consecutive kernel IDs. Mamba groups skip this expansion.
  6. The dispatch: engine.batch_transfer_sync_write(remote_session, src_ptrs, dst_ptrs, lengths). This is the RDMA one-sided WRITE into the D’s registered memory, no D-side CPU involvement.

Async orchestration

  • Two background threads each running their own asyncio event loop (_async_loop): sender loop on P, receiver loop on D.
  • On P, _mooncake_sender_listener accepts ZMQ requests and dispatches to _sender_worker coroutines (num_sender_tasks = 2 × num_workers) which pull from a queue.
  • The actual batch_transfer_sync_write call is offloaded to a ThreadPoolExecutor via run_in_executor since it’s a blocking C call. Each executor thread is bound to the correct CUDA device via _bind_sender_thread_device — CUDA context is thread-local, so this is essential for NVLink transfers on TP > 0.

Special cases

  • Mamba/GDN on the P side truncates the last prompt token (_truncate_mamba_request_for_prefill) so P computes h(N-1), then D recomputes the final token to derive h(N). This avoids sending a state that would need immediate refresh.
  • Sliding-window HMA clips block IDs to the last blocks_per_sw blocks so old windows aren’t wastefully transferred.
  • Timeout handling — SendBlockMeta.expire_time plus fetch_finished_sending_reqs reap stranded P-side blocks if D never asks for them.
  • P/D asymmetry in stats — only P sees successful transfer latency/bytes; D only records recv failures because it never touches the successful path.

KV cache layout

get_required_kvcache_layout returns "HND" for non-MLA models, so layout is forced to [num_heads, num_blocks, block_size, head_dim] and heterogeneous TP transfers are contiguous on the head dimension.

3. MooncakeStoreConnector — Shared distributed KV pool

Fundamentally different model: instead of P pushing to D, both instances independently read from and write to a MooncakeDistributedStore — a shared KV cache pool indexed by content hash.

Why the two connectors are not interchangeable

  • P2P connector: dedicated P and D roles, one-shot transfer per request, no cross-request reuse across instances.
  • Store connector: any instance can be both producer and consumer. Blocks are keyed by hash, so if two requests share a prefix (even across instances), the second one reads from the store instead of recomputing. This is prefix caching at the fleet level.

Structure

  • Delegates to MooncakeStoreScheduler and MooncakeStoreWorker. The connector file is mostly a thin dispatcher.
  • No layerwise saving/loading (save_kv_layer / wait_for_layer_load are no-ops). Puts and gets are batched and issued from get_finished for compute overlap.

Prefix-cache reset

reset_cache drains the send queue then calls remove_all on the Mooncake master. Caller must pause generation first so nothing races in during drain. Only meaningful on the scheduler role.

KV events (MooncakeStoreKVEvents)

Because this is a shared store, other instances care when blocks are added/evicted. The connector emits KVCacheEvents that a KVEventAggregator collects from all workers, dedups to “common events” (present on all workers), and publishes. That’s what powers external prefix-index consumers.

Cross-layer blocks

Opt-in via enable_cross_layers_blocks. Store handles get one large registered tensor across layers instead of per-layer registrations. Only supported for models without hybrid attention.

Config validation

Explicitly rejects:

  • CrossAttentionSpec (encoder-decoder cross-attn).
  • Mamba layers that aren’t in “align mode” (spec.block_size != cache_config.block_size) — needed because the store keys on logical blocks.
  • Hybrid attention combined with prefill/decode context parallelism > 1.

Load-error reporting

Exposes get_block_ids_with_load_errors so the scheduler can invalidate a bad prefix hit and fall through to local recompute. The P2P connector has no equivalent because a failed transfer aborts the whole request.

Store connector flow

─── Producer side (any instance) ───────────────
Scheduler: update_state_after_alloc → mark blocks to store
Scheduler: build_connector_meta → MooncakeStoreConnectorMetadata

Worker: get_finished(finished_ids, metadata)
└── MooncakeStoreWorker.get_finished(...)
    └── enqueue puts to background thread
        └── store.batch_put(keys=[hash(block)], values=[tensor_slice])
              # Mooncake distributed store handles RDMA internally
        └── emit KVCacheEvent(BlockStored, hash) → aggregator → take_events

─── Consumer side (any instance) ───────────────
Scheduler: get_num_new_matched_tokens
└── MooncakeStoreScheduler probes store for block hashes → returns hit count

Scheduler: build_connector_meta → keys to fetch
Worker: get_finished(...)
└── MooncakeStoreWorker.get_finished(...)
    └── store.batch_get(keys) → writes into registered KV memory
    └── on failure: get_block_ids_with_load_errors() → scheduler recomputes

Key differences vs the P2P flow:

  • No ZMQ side-channel, no bootstrap HTTP — the Mooncake master is the single rendezvous.
  • No _sender_listener / _sender_worker machinery. Both put and get are issued from inside get_finished (start_load_kv is a no-op) so they naturally overlap with compute.
  • No P-D asymmetry: any instance does both puts and gets. Prefix reuse across requests and across instances is automatic because keys are content hashes.

4. Quick comparison

MooncakeConnector (P2P) MooncakeStoreConnector
Transfer model P pushes RDMA writes to D Both put/get against shared store
Discovery Bootstrap HTTP + ZMQ side-channel Mooncake master
Backend call batch_transfer_sync_write MooncakeDistributedStore put/get
Prefix cache reuse Per-request only Fleet-wide via content hash
Best for Single P→D pair, low latency Many-to-many, high prefix hit rate
Hybrid KV support Yes (careful group-preserving logic) Yes, with Mamba align mode required

Both implement SupportsHMA so they interop with hybrid attention KV cache managers, and both go through the scheduler/worker split so the scheduler process only tracks metadata while worker processes own the actual device memory registrations.
