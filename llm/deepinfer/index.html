DeepInfer：为什么做，效果如何

《DeepSeek V4.1 Flash 大规模推理部署实践》：

设计目标
  1. 兼容多种厂商的计算芯片
  2. 常见 8 卡做 Prefill，64–128 卡超节点做 Decode
  3. KVCache 保留 72 小时以上

围绕这些目标，Deepseek持续优化计算、通信、调度与存储，在满足延迟要求的前提下提高系统的有效吞吐，用更少的算力与能源支撑更多请求，让智能服务以更低的价格触达更多用户。

线上数字
  • 单集群 155 万亿 tokens/天
  • 整体收入 $38/GPU-hour（谷价）
  • 输入缓存命中率 96%
阶段 指标 实测
prefill 每卡吞吐（不含缓存命中） 60K tps
prefill 每卡吞吐（含缓存命中） 1.5M tps
prefill 平均输入缓存命中率 96%
prefill TTFT 平均 / P99 400 ms / 1000 ms
prefill 平均输入长度 77K tokens
decode 每卡吞吐 14K tps
decode 吐字速度 230 tps（代码 300）
kvcache 不活跃后保存 72 小时
1.5M tps 的关键是 96% 的缓存命中！
实际部署 P:D 接近 1:1。来源：DeepSeek 知乎。

概览 & 架构

  • 平台：GPU + Ascend NPU
  • 自研算子：FlashMLA / DeepGEMM / DeepEP / Tile Kernel
  • 边界：离线推理，不能上线
  • 缺什么：API Server / TP & PP / 量化 / 负载均衡 / KV 传输 & KV 池

01｜C++ Scheduler

一句话：把 调度、block 分配、序列状态更新、输出构造全部搬进 C++。

优点
  • 极致低开销：每步省掉大量 Python 结构体 / 循环 / List / 结构体 / GC
  • 调度期间释放 GIL，可与其他 Python 线程重叠 （e.g. KV 池 / KV 传输 / ZMQ 通信 / 打包输出）
代价
  • 改策略要写 C++；
  • 调试跨 pybind；
  • 基本无法跟 vLLM 上游 merge。
原理
  1. C++ Scheduler 持有 BlockManager + Block Pool + State Pool
  2. 进 / 出 Scheduler 会释放 / 加上 GIL 锁
  3. Block / State Pool 由 C++ Mutex 上锁
  4. 调度输出是 std::vector<std::shared_ptr<Sequence>>，并构造numpy view 提供给 Python 侧
struct Sequence {
  int64_t seq_id;
  std::string request_id;
  std::vector<int> token_ids;
  int prompt_len;
  int block_size;
  int num_tokens; // 已提交 KV cache token 数
  std::vector<int> block_table;
  std::vector<int> accepted_tokens;
  // ...
};

02｜PD 混部调度策略

一句话：每 N 个 decode step 在 DP 组内投票，决定这一步全组做 prefill 还是 decode

优点
  • ANY step 防止 prefill 请求积压
  • ALL step 防止个别 rank 空转
  • 步型一致 → EP all-to-all / CUDA graph shape 稳定
  • 模型前向无混批，逻辑单一，方便算子优化
代价
  • prefill 要等几十个 decode step，TTFT 变差
  • 生产场景基本不会用
原理
bool is_any_point; // 第 0 步不能算 ANY 步
bool is_all_point; // 第 0 步可以算 ALL 步
if (!is_any_point && !is_all_point) 
  return _schedule_decode(acquire);   // 绝大多数步走这里
bool want = cache_usage() <= 0.9 && _has_prefill_waiting();
bool do_prefill = is_any
  ? _dp_allreduce(want ? 0 : 1, MIN) == 0   // 任一想做
  : _dp_allreduce(want ? 1 : 0, MIN) == 1;  // 全员想做
if (!do_prefill) 
  return _schedule_decode(lock);

// 即便是 want, 也有可能因为 KV 不够不能调度 prefill 请求
// 后续还会有二次投票，若全员无法调度则退回 decode
  • 注：_dp_allreduce 走 CPU gloo

03｜Zero-Overhead Scheduler (ZOS)

一句话：GPU forward(N) 掩盖 CPU schedule(N+1) / post-process(N-1)

优点
  • GPU 接近或达成零气泡
  • 压榨极限 TPOT
代价
  • CPU / GPU 账本分离
  • CPU 的调度 / 分配逻辑要考虑 inflight tokens
// seqlen_k = 已提交 KV + 已发射未回填的 KV + 本步 query
int seqlen_k = num_tokens + total_inflight_tokens + seqlen_q;

// GPU 修正 metadata.seqlen_k：去掉本步 query，再退掉未接受的 draft
seqlens_k_base  = metadata.seqlen_k - seqlen_q;
seqlens_k_base -= nextn - prev_num_accepted;
原理
  1. 按 total_inflight_tokens = nextn + 1 乐观预留 block
  2. 乐观推进 Metadata: seqlens / KV len / max position
  3. Sample 之后，在 GPU kernel 修 seqlens，再回传给CPU

04｜模型架构 & KV Cache 格式

绿框 Full = L2/L8/L14/L20，只有它们写 paged KV；黄框 Reuse 复用前一层 Full 的 KV；蓝框 Reindex 复用 L20 的 KV、自算 top-k。
四类 Cache
Cache Type 生产层 格式 每 token
Compressor ca_cache L2/8/14/20 FP4/BS16 288 B
Indexer ica_cache L2/8/14/20 FP4/BS32 68 B
SWA 20 (E) + 23 (D) FP8/BS32 528 B
State L2/8/14（C2） FP32 -
KV Cache Format
  • 两个 raw tensors:
# 储存 ca_cache + ica_cache, block_size = 128
cache_tensor: (num_blocks, block_size_bytes = 113920 B)
# 储存 SWA cache + state
state_tensor: (num_slots = 1.2 * max_num_seqs, state_size_bytes = 3128928 B)
  • 每种 cache 是 raw_tensor 的 strided view, e.g.
ca_cache: [num_blocks, block_size // ratio, 1, bytes_per_token]
ica_cache: [num_blocks, block_size // ratio, 1, index_bytes_per_token]
ca_state: [num_state_seqs, ring_size = 7, 2, dim]
swa_cache: [num_state_seqs, swa_block_size = 134, 1, 528]
  • 非状态类 KV Cache 占用为
(288 + 68) * (3/2 + 1) = 890 B / token
  • 未闭合 C2 state 每请求占用为
ring_size * 2 * dim * fp32_bytes = 7 * 2 * 512 * 4 = 28672 B
  • Indexer 的输入是 compressed latent，无 C2 state，ica_state字段实际没用

05｜前缀缓存

原理
  • 前缀命中由 3FS + entrypoint 算好后通知 Engine
  • BlockManager 只是带 refcount / pin / unpin 的空闲链表，不储存 hash
  • 若前缀命中，Engine 侧会 fork_seq
优点
  • 简化引擎（前缀匹配在 Router / LB 侧本来也要做一遍, e.g. Mooncake）
  • Block KV 留存超 72 小时，提升命中率
  • 极致性能，省掉 hash 开销
命中逻辑
  1. 输入长度 L, 最大命中 L - 128 - 6
  2. 查询 block KV 命中，128 倍数向下取整
  3. 查询 SWA KV 命中，128 倍数向上取整

06｜SWA Bounded Replay

背景
  • 精确重建需要重算 n_layers * n_win tokens：很贵
  • SWA KV 的生命周期本来就不长：分钟级
算法

1. Encoder SWA Bounded Replay

  • 假设 prefill 时前缀命中长度 L， 但SWA KV miss
  • 重放L - 128 ~ L，生成 SWA KV，但不覆盖 block KV
  • 未命中的部分正常前向，生成 SWA + block KV

2. Decoder SWA Bounded Replay

  • 假设 prefill prompt 长度为 L
  • 前 L-128 tokens 只跑 Encoder, 只生成 Encoder SWA KV
  • 最后 128 tokens 跑 Encoder + Decoder，生成 E+D SWA KV
收益
  • 存储上：SWA KV 可以按分钟级别丢弃
  • 计算上：
    • Prefill 计算量 / 激活量减半
    • 前缀匹配可容忍 SWA KV miss，且可以控制重算代价
代价
  • 数学上与精确重算不等价，可能会给精度对齐带来困难
  • 论文 argue 几乎不影响生成质量（SWA 感受野其实没那么大）
  • 训练侧需要模拟 Bounded Replay

07｜DSpark：变长投机验证

一句话：draft 每步固定生成 5 个，但按 confidence 把所有请求的所有 draft 排序，选一个全局预算，使“期望接受 token 数 / 预计 step 时间”最大。

目标
  • 调整总验证预算 $B$ 和每请求预算
  • 最大化吞吐 $\tau\cdot\text{SPS}(B)$
代价
  • 调度与采样逻辑变复杂
  • 低并发可能负收益
  • 需要在线维护时间模型 $\text{SPS}(B)$
算法
  1. 先用 N-2 轮数据选取最优 $B$ (CPU 调度侧)
  2. 再用 N-1 轮置信度贪心地分配预算
  3. 例: num_req = 3, nextn = 2, B = 6 | seqlen_q=[3,2,1]

08｜并行：DP x CP-Attention + EP-MoE + EPLB

DP x CP Attention
  • DP x CP 布局，CP 域在更高速的通信域里
  • 无 TP All-reduce，节省通信但增加权重占用
  • Balanced (Zigzag) CP 布局，平衡 Attn KV 计算量
  • 需要 All-gather latent KV (通信量很小)
  • KV 通信可以和 Q 分支的计算掩盖
  • 少数长请求的情况下，负载比 DP 更均衡

EP & EPLB

  • Wide-EP 64 - 128, 但 A2A 受最慢卡约束

  • EPLB 的目标是极小化 $\sum_i \max_{e}(\text{load}_e / \text{count}_e)$

  • 先决定给哪个专家增加副本；再贪心地选择把副本放到哪张卡

  • 重排的权重搬运，单机内走symm_mem IPC，跨机走 NCCL

  • Prefill: 冗余 4 / 每 100 步统计 / 每 1k 步重排 / moe_lb = slowest / mean = 1.074 (EP4)

  • Decode: 冗余 1 / 每 1k 步统计 / 每 10k 步重排 / moe_lb = 1.090 (EP64)

总结

  • Infra 指导模型架构 (CED / CSA / Hier Indexer)
  • 低开销异步调度
  • 融合算子 / 并行设计 / Bounded Replay 降低时延
  • DSpark 置信验证提升吞吐

但是

  • DS V4.1 极致高性价比主要来源于超高前缀命中率
  • 分布式 KV 池的硬件、Infra 和留存策略很关键
  • 未必算是开源了印钞机

思考

  • 框架的发展路线可能是模型特化(Qwen, Hy, DS)、硬件特化（计算架构、内存架构、算力带宽比）
  • 大规模部署要配套相应的分布式 KV 池 (e.g. Mooncake Store)
